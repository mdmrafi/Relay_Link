# Firestore Schema — RelayLink

This document is the canonical schema for the Cloud Firestore collections
that RelayLink uses. It is generated alongside `lib/backend/schemas.dart`
(Ticket #18) — keep the two in lockstep; the Dart-side constants are the
typed mirror of the field names listed here.

## Collections

| Collection                              | Path                                                  | Source ticket | Purpose                                            |
|-----------------------------------------|-------------------------------------------------------|---------------|----------------------------------------------------|
| `relay/{channel_id}/messages`           | BROADCAST mesh messages, grouped by channel             | #18, #20      | Outgoing broadcast, incoming gateway pull          |
| `relay_direct/{recipient_id}/messages`  | DIRECT mesh messages addressed to one recipient        | #18, #20      | Outgoing direct, incoming device or gateway pull   |
| `verified_orgs/{org_id}`                | ALERT verification allowlist (human-curated)           | #18, #35, #36 | Receivers consult this to badge ALERT messages    |
| `evidence/{recipient_id}/records`       | Evidence Vault text uploads                            | #18, #31      | Encrypted text records sent to a chosen recipient |

All four collections are written from the device using the sender's
pseudonymous Ed25519 identity (no Firebase Authentication). There is no
account system; "identity" is the device's keypair (see §6 of the spec).

## `relay/{channel_id}/messages` schema

Path: `relay/{channel_id}/messages/{message_id}`

Field `message_id` is the document id, a UUIDv4 generated by the sender
(`uuid` package, Ticket #04). The same id is stored in the `id` field so
clients can index it without reading the document id.

| Field           | Type             | Required | Description                                                                                            |
|-----------------|------------------|----------|--------------------------------------------------------------------------------------------------------|
| `id`            | string (UUIDv4)  | yes      | Message id. Matches the document id.                                                                   |
| `sender_id`     | string           | yes      | Ed25519 public-key fingerprint of the sender. Routing metadata, plaintext.                            |
| `created_at`    | Firestore `Timestamp` | yes  | Server timestamp when the gateway wrote the document.                                                  |
| `payload_b64`   | string           | yes      | Base64 ciphertext. BROADCAST: AES-256-GCM with channel key. DIRECT: ratchet session key.              |
| `ratchet_header`| string \| null   | no       | Plaintext ratchet header for DIRECT messages. `null` for BROADCAST.                                   |
| `ttl`           | number (int)     | yes      | Time-to-live in minutes. SOS 12, ALERT 10, others 8 (per SPEC §5).                                    |
| `hop_count`     | number (int)     | yes      | Hops traversed. Starts at 0 at sender, incremented by each relay. Hard cap enforced in rules.          |
| `signature`     | string           | yes      | Ed25519 signature over `id|sender_id|created_at|payload_b64|ttl|...` (canonical form per crypto ticket). |
| `expires_at`    | Firestore `Timestamp` | yes  | When the server should delete this document. Read by the Firestore TTL policy. **Required on every write.** |

## `relay_direct/{recipient_id}/messages` schema

Path: `relay_direct/{recipient_id}/messages/{message_id}`

Same field set as `relay/{channel_id}/messages`. The difference is the
subcollection layout: messages here are addressed to a single recipient
device id (`recipient_id` is the path segment, not stored in the document),
which lets the recipient's device or a Gateway pull only its own slice
rather than scanning the full broadcast feed.

The same `expires_at` field is required so the TTL policy covers both
relay collections uniformly.

## `verified_orgs/{org_id}` schema

Path: `verified_orgs/{org_id}`

| Field           | Type             | Required | Description                                                                              |
|-----------------|------------------|----------|------------------------------------------------------------------------------------------|
| `id`            | string           | yes      | Document id. Human-readable slug, e.g. `demo-red-crescent`.                              |
| `display_name`  | string           | yes      | Display name for the verified badge, e.g. "Demo Red Crescent Branch".                    |
| `public_key_b64`| string           | yes      | Base64-encoded Ed25519 public key. Verified ALERT signatures must match this.            |
| `last_updated`  | Firestore `Timestamp` | yes  | Last server-side refresh of this row. UI uses this to warn about stale allowlist.        |
| `expires_at`    | Firestore `Timestamp` | yes  | TTL expiry. The allowlist is stable; the field exists so the same TTL policy covers it. |

There is **no** field a sender can set on a Message to claim verification
("verified": true or similar). Verification is a receiver-side check:
the recipient computes the SHA-256 of the sender's `public_key_b64` and
looks it up in the locally cached allowlist. Match → verified badge. No
match → standard "signed by [device]" label. This is deliberate; allowing
sender-side self-assertion would be trivially spoofable.

## `evidence/{recipient_id}/records` schema

Path: `evidence/{recipient_id}/records/{record_id}`

| Field              | Type             | Required | Description                                                                                              |
|--------------------|------------------|----------|----------------------------------------------------------------------------------------------------------|
| `id`               | string (UUIDv4)  | yes      | Document id. Same as the record id on the recipient side.                                                |
| `recipient_id`     | string           | yes      | Recipient device id (Ed25519 fingerprint).                                                               |
| `sender_id`        | string           | yes      | Sender device id (Ed25519 fingerprint).                                                                  |
| `created_at`       | Firestore `Timestamp` | yes  | Server timestamp when the record was uploaded.                                                          |
| `payload_b64`      | string           | yes      | Base64-encoded double-sealed ciphertext (per-record key, then vault-wrapping key).                      |
| `content_hash_b64` | string           | yes      | Base64 SHA-256 of the plaintext. Lets the recipient verify decryption without re-reading the original.   |
| `signature`        | string           | yes      | Ed25519 signature over `id|sender_id|recipient_id|created_at|content_hash_b64`. Authenticates the sender. |
| `expires_at`       | Firestore `Timestamp` | yes  | TTL expiry. Evidence is short-lived; the vault is "deliver to my contact", not "store forever".         |

Payload is end-to-end encrypted. The Firestore server sees only the
ciphertext and the metadata fields above.

## Server-side TTL

Every doc in every collection carries an `expires_at` field. The
production deployment configures a Firestore TTL policy in the Firebase
console to delete documents at or after `expires_at`. **The TTL policy
is not an SDK concern — it is a one-time setup step in the Firebase
console.** See the README for the exact steps.

The policy scopes to each collection's `expires_at` field and runs on
Firestore's normal compaction cadence (typically within 24 hours of
expiry, per Google's docs). This is good enough for ephemeral relay
traffic; it is not a real-time deletion primitive.

## Security rules (sketch)

The full rules file lives at `firestore.rules` (added in a follow-up
ticket). The minimum behavior to encode when the file lands:

- Read/write to `relay/*` and `relay_direct/*` from any client (no auth)
  is permitted, but **rate-limited** and **size-limited** per spec §9.
- Read/write to `verified_orgs/*` is restricted to a small set of
  curator accounts (not implemented for the demo; the file content is
  seeded by hand).
- Read/write to `evidence/*` requires the document's `recipient_id` to
  match the device's public-key fingerprint (verified via the device's
  identity key).

## Drift warning

If a field name in this file differs from the constants in
`lib/backend/schemas.dart`, treat the discrepancy as a bug — the Dart
side is what the running app actually reads. Update the doc first, then
the Dart constants, then commit.
