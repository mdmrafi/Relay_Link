## 1. What this is, in one paragraph

RelayLink is an offline-first Flutter app: devices are supposed to swap short encrypted messages over Bluetooth mesh, SMS, or the internet, buffer what they receive, and forward it opportunistically, with an opt-in "gateway mode" that relays mesh traffic through Firestore without the gateway ever seeing plaintext. Large parts of this are real, tested, production-quality Dart: the crypto, the message/relay/bloom-filter logic, the vault, the UI screens. The app-level wiring gap described in §3 is now closed — `lib/main.dart` constructs the production transports, crypto, persistence, and chat controller at boot, and a single device can exercise the full send → fan-out → incoming → decrypt → render path via `--dart-define=DEV_LOOPBACK=true`. Real radio backings and a real Firebase project are still stubs (§7, §8).

**Net result:** `lib/main.dart` constructs `LocalDb`, `DeviceIdentity`, `DirectSessionStore`, `TransportManager` (with `MeshTransport`, `SmsTransport`, `InternetTransport` registered; `InternetTransport` registers against a `_UnavailableFirestoreGateway` that throws `FirestoreGatewayUnavailable` so it never silently falls back to "no-op success"), `BroadcastCrypto`, `RepositoryContactsLookup`, and `RemoteChatController` once at boot. `ChatScreen` is backed by `RemoteChatController` (production impl of the abstract seam). `BroadcastCrypto.decryptString` and `DirectSession.decrypt` are wired as the chat's `MessageDecryptor` (mode-dispatched).

**What this still leaves open:**
- The three transports register but their `isAvailable()` returns false because their platform backings are still stubs (§7). `MeshTransport` and `SmsTransport` throw on platform calls by design; `InternetTransport` is the `_UnavailableFirestoreGateway` no-op.
- With `--dart-define=DEV_LOOPBACK=true`, an `EchoTransport` is registered last so a single device can verify the full send → fan-out → incoming → decrypt → render path end-to-end.
- The QR-scanner UI for the invite is deferred to a follow-up; pairing is currently via paste (token in clipboard → paste into the dialog → Pair).

**Mesh / internet transport wiring is explicitly out of scope** for this plan — they need real radio / Firebase backings first (§7, §8) before the registration wiring would mean anything more than it does today.

## 7. Pure stubs — code exists as a seam, no real backing implementation

- **BLE mesh radio (Android):** `StubMeshDiscoveryPlatform` in `lib/mesh/discovery.dart:202`. `connect()` throws `StateError` by design. No `flutter_nearby_connections` (or equivalent) in `pubspec.yaml`. The `MeshTransport` registers fine; its `send` will throw when called because the discovery never connects.
- **iOS Multipeer Connectivity:** `StubMultipeerDiscoveryPlatform` in `lib/mesh/discovery_ios.dart:161`. File header documents the exact migration plan (add `nearby_connections`, set `Info.plist` keys, branch on `Platform.isIOS` in `main.dart`).
- **Wi-Fi Direct (Android):** `StubWifiDirectPlatform` in `lib/mesh/discovery_wifi_direct.dart:146`. Same pattern.
- All three share one `MeshDiscoveryPlatform` contract and an in-process `Loopback*Platform` test fake, so writing the real backing implementation for one is a good template for the other two. None of the three can be verified end-to-end without a real device/emulator with the relevant radio — they'll compile and pass fake-backed unit tests regardless.
- **Vault media (photo/video/audio):** not started at all — not a broken seam, just an unbuilt feature. `lib/vault/store.dart` is deliberately text-only today; the UI discloses this. Would reuse the same AES-256-GCM key ladder.
- **`FirestoreGateway` real backing:** `lib/backend/firebase.dart` and `firebase_options.dart` are correct and complete; the bootstrap's `_UnavailableFirestoreGateway` is the honest stub used in place of a real project (§8).

## 8. Blocked on something only a human can do

- **Real Firebase/Firestore project.** `lib/backend/firebase.dart` and `firebase_options.dart` are correct and complete; no production project is bundled (correctly — this is a public/hackathon repo). Someone needs to create a real Firebase project and drop in real config before gateway mode or internet transport mean anything beyond local-only fallback. Once that happens, replace `_UnavailableFirestoreGateway` in `lib/app/bootstrap.dart` with the real gateway — no other wiring change is required.
- **Verified-org production trust source.** `lib/allowlist/verified_orgs.dart` deliberately hard-refuses any allowlist entry without `"demo": true` — this is a safety gate, not a bug. `assets/verified_orgs.json` ships 3 demo entries. The client-side fetch/cache/signature-verify code is easy to build and test against a fake signer; there is no real signing authority to point it at — that's a decision about who gets to vouch for "verified" orgs, not a coding task.

## 9. Hard platform restriction — not a code gap, don't file it as one

**iOS SMS.** `lib/sms/platform_channel.dart` throws on iOS by design. Apple provides no API for a third-party app to send SMS silently — full stop. The only legitimate iOS path is popping `MFMessageComposeViewController` for the user to review and tap Send themselves, which changes the UX contract from "automatic relay" to "user-confirmed compose." If iOS SMS support matters to you, that's a product decision to make explicitly before anyone writes code, not a bug to fix.

## 10. Recommended order if you want a roadmap

Feasibility-first, not urgency-first — pick based on what you actually want to demo next:

1. **Wire a real radio backing** (Wi-Fi Direct, iOS Multipeer, or BLE) — write the platform binding for one, accept that you can't verify it here without hardware. The `TransportManager` registration path is already done; this is purely the radio layer underneath `MeshTransport`.
2. **Real Firebase project** — someone with an account needs to drop in real config and replace `_UnavailableFirestoreGateway` in `lib/app/bootstrap.dart`. This unlocks `InternetTransport` and gateway mode for real.
3. **QR-scanner UI for `ContactInvite`** — the codec + paste-pair flow ship today; the camera scanner is a small widget on top. Pick a `mobile_scanner` / `qr_code_scanner` package and wire the dialog's clipboard-paste path to it.
4. **Vault media** — large but fully buildable without external accounts (capture UI needs a device to fully exercise; storage/crypto logic doesn't).
5. **Verified-org fetcher client code** — buildable against a fake signer now; flag that a real trust authority is a separate, non-technical decision.
6. **`DoubleRatchetSession` adoption** — replace `DirectSession` (HKDF-chain) in `RemoteChatController.sendDirectMessage` with `DoubleRatchetSession` (full Signal-spec ratchet with skipped-key map + DH step). Pure library swap, no wiring change.
7. **iOS SMS** — needs a product decision (§9) before any code.
